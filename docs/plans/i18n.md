# Internationalization

WordPress has two i18n problems. It solved one of them well and punted on
the other for twenty years.

**Problem 1 — UI translation.** The admin panel, theme strings, error
messages, date formats. WordPress solved this with gettext (.po/.mo files)
and a global translation community. It works. The system is mature.

**Problem 2 — Content translation.** Translating blog posts. WordPress
never built this in. The community produced plugins — WPML, Polylang,
TranslatePress — each with a different data model, each fighting the core
schema. Some created separate posts per language. Some stored translations
in postmeta. Some ran separate sites in multisite. All of them were bolted
on, and all of them were fragile.

Press should solve both.

---

## UI Translation

### The Problem

Every string the user sees — "Published", "Save Draft", "Categories",
"Older Posts", "Leave a comment" — needs to be translatable. This includes
the admin interface and the default theme.

### Direction

Go has `golang.org/x/text/message` for string translation with plural
support. The pattern:

```go
p := message.NewPrinter(language.French)
p.Printf("Published on %s", date)
```

Translation catalogs are Go files or JSON — no binary .mo compilation
step. Translators work with plain text.

Theme strings use the same system. Template functions wrap translatable
strings:

```html
<button>{{ T "Save Draft" }}</button>
<p>{{ TN "%d comment" "%d comments" .Post.CommentCount }}</p>
```

`T` is the translation function in the funcmap. `TN` handles plurals.
A theme author writes English strings. Translators provide the
alternatives.

### What We Need

- A `T` function in the template funcmap
- Translation catalogs (JSON or Go) per language
- Language selection — from `.env`, `wp_options`, or browser
  `Accept-Language`
- Date and time formatting respecting locale

### What We Don't Need

- Runtime language switching per-user (single-author blog, one language)
- .po/.mo toolchain — Go's native catalog format is simpler
- Translation management UI — translators edit files

## Content Translation

### The Problem

A blogger writes in English. They want a French version of the same post.
Not a different post — the same post, in another language. Linked, so a
French reader landing on the English version can switch. Maintained, so
when the English version is updated the French translation is flagged as
potentially stale.

WordPress never solved this because the post model assumes one post, one
content column, one language. Every plugin invented its own workaround.

### The Approaches That Failed

**Separate posts per language (WPML, Polylang):**
Create a French copy of the English post. Link them via postmeta. Now you
have two posts that are conceptually one thing. Slugs diverge. Categories
diverge. The relationship is metadata, not structure. Delete the original
and the translation is orphaned.

**Postmeta storage:**
Store translations in `post_content_fr`, `post_content_de` as meta keys.
The content column holds one language, meta holds the rest. Doesn't scale.
Can't query translations. Can't paginate translated post lists without
custom queries for every language.

**Multisite:**
One site per language. Same content duplicated across databases. The
nuclear option. Works for large publishers. Absurd for a personal blog.

### Direction

The translation is a property of the post, not a separate entity. A post
has content in one or more languages. One language is the original. The
others are translations of it.

Possible model — a `wp_translations` table:

```sql
CREATE TABLE wp_translations (
    translation_id  INTEGER PRIMARY KEY AUTOINCREMENT,
    post_id         INTEGER NOT NULL,
    language        TEXT    NOT NULL,       -- BCP 47: 'en', 'fr', 'ja'
    title           TEXT    NOT NULL DEFAULT '',
    content         TEXT    NOT NULL DEFAULT '',   -- ProseMirror JSON
    excerpt         TEXT    NOT NULL DEFAULT '',
    slug            TEXT    NOT NULL DEFAULT '',
    translator_id   INTEGER NOT NULL DEFAULT 0,
    status          TEXT    NOT NULL DEFAULT 'draft',
    source_version  INTEGER NOT NULL DEFAULT 0,    -- version of original this was translated from (mechanism TBD)
    created_at      DATETIME,
    updated_at      DATETIME
);

CREATE UNIQUE INDEX idx_translations_post_lang ON wp_translations (post_id, language);
CREATE INDEX idx_translations_language ON wp_translations (language);
```

The original post lives in `wp_posts` as always. It has a language (stored
in `wp_postmeta` or a column — TBD). Translations live in
`wp_translations`, keyed by post_id and language.

### Why This Might Work

**The original is the original.** `wp_posts` doesn't change. A post with
no translations works exactly like it does today. Zero overhead for
single-language blogs.

**Translations are linked by structure, not metadata.** `post_id` +
`language` is a unique key. You can't have an orphaned translation. Delete
the post, cascade deletes the translations.

**Staleness tracking.** The translation records which version of the
original it was translated from. When the original is updated, the
translation is flagged as potentially stale. The translator sees "the
original has changed since this was translated" and can review what
changed.

**Open:** The staleness tracking mechanism needs more thought. Using
the raw step version won't work because old steps may be trimmed. We
probably need a revision number or content hash on the post itself —
something that persists independently of the step log. This needs a
smart system that doesn't couple translation freshness to step log
retention.

**Each translation has its own slug.** `/en/hello-world/` and
`/fr/bonjour-le-monde/` are different URLs for the same post. The
permalink router resolves the language prefix and looks up the translation.

**ProseMirror JSON throughout.** Translations are ProseMirror documents,
same as the original. Same rendering pipeline. Same editor for translating.

### Language Routing

Two options:

**Path prefix:** `/fr/2024/01/03/bonjour-le-monde/`
The language is in the URL. Clean, bookmarkable, good for SEO. The router
strips the prefix and resolves the rest normally, then looks up the
translation for that language.

**Subdomain:** `fr.example.com/2024/01/03/bonjour-le-monde/`
Familiar pattern, used by Wikipedia. More DNS configuration. Probably
overkill for a blog.

Leaning toward path prefix. Simpler, no DNS requirements.

**Open:** Language routing needs to be reconciled with the permalink
system described in `docs/plans/permalinks.md`. The router compiles the
permalink structure into regex at startup. A language prefix before the
structure would need to be stripped before resolution, or the router
would need language-awareness built in. This is a non-trivial routing
change that needs to be figured out when we build both systems.

### The Translation Workflow

This is where the collaboration system pays off. Translating a post is
an editing session:

1. Author marks a post for translation into French
2. Press creates a translation entry with the original content
3. A translator (or the author) opens the translation in the editor
4. Side-by-side view: original on the left, translation on the right
5. The translator works through the document, replacing content
6. `source_version` is stamped with the current step version of the original
7. Translation is published independently of the original

When the original is edited later, translations with a `source_version`
behind the current version show a "needs review" indicator. The translator
can see what changed in the original (via the step log) and update
accordingly.

### AI Translation Assist

This is where the AI writing system (see `docs/plans/ai.md`) becomes
particularly interesting. The AI connects to the translation editing
session and can:

- Propose an initial translation of the full document
- The translator reviews, edits, and approves — same suggested edit
  workflow as any AI writing assistance
- The AI's translation is steps in the step log, attributed to the AI
- The human translator's corrections are their own steps

The AI doesn't replace the translator. It gives them a starting point.
The translator is an editor reviewing AI output, not typing from scratch.

## What We Build Now

Nothing i18n-specific. But the prerequisites matter:

1. **ProseMirror JSON content** — translations store the same format
2. **Step log with versioning** — powers staleness detection
3. **Collaboration infrastructure** — the translation editor is a
   collab session
4. **Template funcmap** — `T` and `TN` can be added when we build themes

## What We Don't Build Yet

- `wp_translations` table
- Language routing in the permalink system
- Translation editor UI (side-by-side view)
- AI translation integration
- UI translation catalogs (English-only at first)

## Open Questions

- **Does the original post need a `language` field?** Or is the site-wide
  language setting enough? A multilingual author might write some posts
  in English and some in French — should language be per-post?
- **Comment translation:** Do comments stay in whatever language they were
  written in? Translating comments seems like overkill. But should the
  comment form appear on the translated version of the post?
- **Feed per language:** Should `/feed/` serve the site language and
  `/fr/feed/` serve French posts? Probably yes.
- **hreflang tags:** The rendered HTML should include `<link rel="alternate"
hreflang="fr" href="/fr/...">` for SEO. This is straightforward once
  translations exist.
